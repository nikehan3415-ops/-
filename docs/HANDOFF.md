## 3. 분석 결과 (ROM 구조)

### 3.1 문자 인코딩

- 텍스트는 **16비트 리틀엔디언** 토큰으로 되어 있습니다. 0x0000~0x000F는 제어 코드이고, 0x0010부터 글자입니다.
- 글자 순서표는 ROM **0x0BCE20**에 있는 디버그용 SJIS 테이블입니다. 2바이트 SJIS × 0x6D0개이며, 인덱스가 곧 코드입니다(0x00~0x0F 자리는 공백으로 채워져 있음).
  - 이 테이블을 참조하는 코드는 `0x080470A0` 부근(SJIS를 디버그 폰트로 변환)입니다. 디버그 8x8 폰트는 `0x08615C2C`이고, 앞 0x100자만 씁니다.
- 테이블 끝 부근 0x6CA~0x6CF는 공백으로 채워져 있지만 실제로는 글리프가 있습니다. 0x6D0 이상은 테이블에 없는 한자입니다. 문맥으로 추정한 것은 `tables/top_jp.tbl`에 기록했습니다.

| 코드 | 추정 | 근거 문맥 | 코드 | 추정 | 근거 문맥 |
|---|---|---|---|---|---|
| 06CA | 杯 | 精一杯, 乾杯 | 06CF | 販 | 販売 |
| 06D3 | 掴 | 手がかりが掴めました | 06D4 | 貰 | 貰っておく |
| 06D7 | 療 | 治療 | 06DC | 余 | 余計 |
| 06FA | 齢 | 老齢 | 06FB | 叔 | 叔父 |
| 06FC | 詮 | 所詮 | 06FD | 薪 | 薪がなくなる |
| 06FE | 岐 | 分岐点 | 06FF | 罰 | 罪に対する罰 |

- 미확인 글자: **06D1**(「わしを?んでいる」, 恨은 0x511에 이미 있으므로 憎 또는 怨으로 추정), **06CB~06CE**(볼트 대사에 쓰이는 기호 문자). CSV에는 `{G:6D1}` 형식으로 들어 있습니다.
- **메인 폰트의 위치는 아직 찾지 못했습니다.** 한글 폰트를 넣으려면 반드시 찾아야 하는 다음 과제입니다(§5-2).

### 3.2 대사 데이터 위치와 구조

- **블록 포인터 테이블**: `0x27474C`, u32 × 54개(`0x08xxxxxx`). 중복이 1개(`0x7ABAA8`) 있어서 서로 다른 블록은 53개입니다.
- **추가 블록**: `0x7BC2A8`. 포인터 테이블에는 없고 코드(ROM `0x5F10` 리터럴)에서 직접 참조합니다. 이것까지 합쳐 총 54블록입니다.
- 블록 영역은 `0x6C7EC4`~`0x7BC4F2`이고, 그 뒤 `0x7C0000`까지는 0으로 채워져 있습니다. 대사는 **압축되어 있지 않습니다**. 앞서 LZ77(BIOS 0x10) 전수 조사에서 대사가 걸리지 않았던 이유입니다.
- 블록 포인터는 **정렬되지 않은(홀수) 주소일 수 있습니다.**

블록 구조:

```
+0x00 u32 script_off   ; 블록 시작 기준
+0x04 u32 text_off     ; 블록 시작 기준
+0x08 u32 event_count
+0x0C event_count × 8B ; (u16 ?, u16 event_id, u32 script_entry) 추정
[script_off] 바이트코드
[text_off]   0x0000으로 끝나는 문자열의 연속
             마지막 문자열 뒤에 0xFF 1바이트(종료), 이후 패딩 0xFF가 올 수 있음
```

- 종료 판정: 문자열이 시작될 위치의 바이트가 `0xFF`이고 **다음 바이트가 0이 아니면** 종료입니다. `FF 00`은 글자 ヴ(0x00FF)라서 이렇게 구분합니다. 이 차이 때문에 초기 파서가 오작동했습니다.
- 스크립트는 문자열을 **텍스트 영역 기준 바이트 오프셋(u16)**으로 참조합니다. 확인한 패턴은 `xx 80 11 <u16 off> 01`(대부분), `12`, `14`, `23` 계열입니다. 오프셋이 홀수일 수도 있습니다. `{VAR}` 등의 식이 홀수 길이라서 문자열 정렬이 깨지기 때문입니다.
  - 확인에 쓴 예: 첫 블록(0x6C7EC4)의 문자열 오프셋 0x9C, 0xC4, 0xEA, 0x122 …가 스크립트에서 `80 11 9c 00 01` 형태로 모두 발견되었습니다.

### 3.3 제어 코드

| 코드 | 인자 | 의미 | CSV 태그 |
|---|---|---|---|
| 0000 | – | 문자열 끝 | (행 구분) |
| 0003 | – | 줄바꿈 | 셀 내 개행 |
| 0004 | – | 키 대기, 다음 페이지 | `{W}` |
| 0005 | u16 | 출력 속도 (10=느림, FF=복귀, 3 등) | `{SPD:x}` |
| 0006 | u16 | 글자색 (2=강조, 0=복귀, 3) | `{COL:x}` |
| 0007 | u16 | 파티원 이름 1~6 | `{N1}`~`{N6}` |
| 0008 | u16 | 아이템 이름 | `{ITEM:x}` |
| 0009 | u16 | 칭호 이름 | `{TITLE:x}` |
| 000A | u32 | 숫자 표시 (예: 0xCF08=53000) | `{NUM:x}` |
| 000B/000C/000D/000E | 스크립트 식 | 변수 표시 등 | `{EXB/EXC/EXD/VAR:hex}` |
| 000F | – | 튜토리얼 문장 끝 (의미 미확인) | `{C:F}` |

- 이름 번호: 1 クレス, 2 ミント, 3 アーチェ, 4 クラース, 5 チェスター, 6 すず.
- 스크립트 식 길이 규칙(`expr_len`): `0x80`=끝, `0xC8`=+2바이트, `0xC0`·`0xE0~0xEF`·`0x40~0x7F`=+1바이트, 그 밖의 바이트=연산자 1바이트.
  - 예: `E1 38 C8 10 27 89 80` → 변수 0x38, 즉값 10000, 연산자 0x89, 끝.
- `000B`는 1회만 나오고 의미도 확실하지 않습니다. 왕복 검증은 통과하지만 재삽입할 때 한 번 더 확인하세요.

### 3.4 대화창 서식

- 1줄 **전각 17자**: 원문 대사 줄의 99.8%가 17자 이하입니다. 17자를 넘는 줄은 제작진 목록, 표지판 같은 특수 화면입니다.
- 1페이지 **최대 3줄**: 화자 이름 줄을 포함합니다. 원문 분포는 1줄 12,241페이지, 2줄 7,907페이지, 3줄 3,724페이지입니다.
- 화자 이름 형식: `이름<3>「대사…」<4>`. 일반 NPC는 이름을 문자열로 직접 쓰고, 파티원은 `<7><n>` 코드를 씁니다.

### 3.5 그 밖의 텍스트 (아직 추출하지 않음)

- **시스템/메뉴 텍스트**: `0x2A0000` 부근. 대사와 같은 16비트 인코딩이며, 도움말·세이브 메시지·몬스터 이름·아이템 이름 등이 있습니다.
- 8비트 가타카나 이름 목록(이름 입력 후보 등): `0x2A5000`~`0x2A7800`. 코드는 같은 테이블 인덱스를 8비트로 씁니다.
- 제작진 목록(성우 이름): `0x25D9E0` (16비트).
- `0x29F800`: 이름 입력 화면용 문자 배열.

### 3.6 분석 과정에서 걸러낸 것 (같은 조사를 반복하지 않도록)

- ROM 안에 SJIS 평문 대사는 없습니다. 0x0BCE20 테이블만 SJIS입니다.
- 4바이트 정렬 LZ77(0x10) 스트림 2,671개를 풀어 봤지만 대사는 없었습니다. 풀린 것은 그래픽과 맵 데이터(맵 포인터 `0x270AAC` 186개, 대상 `0x4BB530~`)입니다.
- 폰트를 1bpp 16px 폭 이미지로 훑어보는 방법(0xD4000, 0x600000 부근)은 실패했습니다. 토큰만 많이 들고 효과가 없었으므로, **코드 추적으로 찾기를 권장합니다**(§5-2).

## 4. 검증 체계

| 단계 | 명령 | 확인 내용 |
|---|---|---|
| 추출 무결성 | `verify` | `japanese` 열을 다시 인코딩해 문자열 단위와 서브블록 텍스트 영역 전체를 ROM과 바이트 비교, 누락·추가 행 검사 |
| 번역 품질 | `check` | 제어 태그 집합 일치, `{W}` 개수와 끝 위치, 태그 괄호 손상, 1줄 17칸(원문이 더 길면 원문 기준), 페이지 3줄 |

- 폭 계산: 이름 태그는 실제 이름 길이, `{ITEM}`/`{TITLE}`은 8칸, 나머지 태그는 0칸.
- 검사기 동작 확인: 가짜 번역 3행(정상 1, 줄 초과 1, 태그 누락 1)을 넣어 오류 2건을 정확히 잡는 것을 확인했습니다.

## 5. 다음 작업 (우선순위 순)

1. **재삽입기** `tools/top_text.py insert`
   - 번역을 인코딩하고 블록 텍스트 영역을 다시 만든 뒤, 스크립트 안의 문자열 오프셋 참조를 새 값으로 바꿉니다.
   - 확실한 방법은 스크립트 바이트코드 opcode 길이표를 만들어 파싱하는 것입니다. 간단한 방법은 `80 11 <old> 01` 패턴을 치환하는 것인데, 오탐 위험이 있습니다.
   - 블록이 커지면 ROM 빈 공간 `0x7C0000~0x7FFFFF`(약 256KB, 0으로 채워짐)으로 옮기고 `0x27474C` 포인터와 `0x5F10` 리터럴을 고칩니다.
   - 텍스트 영역이 64KB를 넘지 않게 해야 합니다(오프셋이 u16).
   - 완료 기준: 번역하지 않은 CSV로 삽입했을 때 원본 ROM과 바이트가 같아야 합니다.
2. **메인 폰트 찾기**: 텍스트 렌더러를 추적합니다. 제어 코드 7(이름)이나 4(대기)를 분기하는 루틴에서 시작해 `ldrh`로 토큰을 읽는 부분을 찾고, 글리프 주소 계산(`code × size + base`)에서 폰트 base와 형식(크기, bpp)을 알아냅니다. 에뮬레이터 VRAM 덤프와 대조하면 가장 빠릅니다.
3. **한글 테이블과 폰트 설계**: 기존 한자 영역을 한글로 교체하거나 코드 영역을 확장합니다. 번역문에 실제로 쓰인 글자만 넣는 방식이 현실적입니다(`check`에 "테이블에 없는 글자" 검사를 추가해야 함).
4. **시스템 텍스트 추출**: §3.5 영역을 같은 도구 구조로 뽑아 `script/system.csv`로 만듭니다.
5. **06D1, 06CB~06CE 글리프 확인**: 폰트를 찾은 뒤 이미지로 확인하고 tbl을 갱신합니다.
6. **에뮬레이터 테스트 환경**: emucap MCP([mcpads/emucap](https://github.com/mcpads/emucap), GBA는 Mesen2 백엔드)를 설치하려 했지만, 이 클라우드 세션에서는 외부 저장소 추가가 권한 정책으로 거부되었습니다. 컨테이너에는 Xvfb가 있습니다. 권한을 허용하거나 로컬 PC에서 설치해야 합니다.

## 6. 주의사항

- `japanese` 열은 검증 기준이므로 절대 수정하지 마세요. CSV 행을 추가·삭제하거나 순서를 바꾸는 것도 금지입니다.
- CSV를 Excel에서 저장할 때는 **UTF-8 CSV** 형식을 쓰세요. 저장한 뒤 `verify`를 다시 실행합니다.
- 추정 한자(§3.1)는 폰트로 확인하기 전까지 번역 참고용입니다. 재삽입에는 영향이 없습니다(코드값을 그대로 다시 씀).
